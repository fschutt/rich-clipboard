# rclip-codepage

Legacy single-byte code page tables, for the clipboard formats that still carry them.

Five codecs in this workspace independently hit the same wall in Phase 0: a payload that says
"these bytes are text" without saying in which encoding, or saying it only as a number.
`CF_HDROP` with `fWide == 0`, `.lnk` `StringData` with `IsUnicode` clear, ANSI shell strings in
an `ITEMIDLIST`, `[InternetShortcut.A]` in a `.url`, and RTF's `\ansicpgN` / `\mac` / `\pc` /
`\pca`. Each of them deferred the problem with a `// TODO(phase-1):` rather than guess. This
crate is the table those five needed.

```rust
use rclip_codepage::Encoding;

// RTF `\ansicpg1252`, .lnk code page fields, CF_LOCALE: all identify an
// encoding by number and nothing else.
let enc = Encoding::from_windows_codepage(1252).unwrap();

assert_eq!(enc.decode_byte(0x93), Some('\u{201C}'));  // left double quote
assert_eq!(enc.decode_byte(0x81), None);              // undefined, not U+FFFD

for c in enc.decode(b"caf\xe9") {                     // borrows, allocates nothing
    let _ = c?;                                       // Err at an undefined byte
}
# Ok::<(), rclip_core::Error>(())
```

`no_std`, `forbid(unsafe_code)`, no dependency but `rclip-core`. The `char` iterators allocate
nothing; `decode_to_string` / `encode_from_str` are behind the `alloc` feature.

## Coverage

| Encoding | Code page | Where it turns up |
|---|---|---|
| Windows-1250 … 1258 | 1250–1258 | RTF `\ansicpgN`; Windows ANSI paths and shell strings |
| Mac OS Roman | 10000 | RTF `\mac`; pre-OS-X resource-fork strings |
| IBM/OEM 437 | 437 | RTF `\pc`; ancient `.lnk` ANSI strings |
| IBM/OEM 850 | 850 | RTF `\pca` |
| ISO-8859-1 | 28591, also 819 | asked for by name; *not* what Windows means by "ANSI" |

Multi-byte pages (932 Shift-JIS, 936 GBK, 949, 950 Big5) and the Unicode ones (65001, 1200,
1201) are deliberately **not** here: `from_windows_codepage` returns `None` for them, because a
single-byte table applied to a DBCS payload produces confident garbage rather than an error.

## Where the tables come from

Generated by [`generate/generate.py`](generate/generate.py) from the Unicode Consortium's
vendor mapping files, not typed by hand. One transposed digit in a 128-entry table is invisible
in review and produces mojibake in exactly one locale.

| Source | Revision generated from |
|---|---|
| `MICSFT/WINDOWS/CP1250.TXT` … `CP1254.TXT`, `CP1257.TXT`, `CP1258.TXT` | table version 2.01, 1998-04-15 |
| `MICSFT/WINDOWS/CP1255.TXT` | table version 2.01, 2000-01-07 |
| `MICSFT/WINDOWS/CP1256.TXT` | table version 2.01, 1999-01-05 |
| `MICSFT/PC/CP437.TXT`, `CP850.TXT` | table version 2.00, 1996-04-24 |
| `APPLE/ROMAN.TXT` | revision c02, 2005-04-05 |

Each file is pinned by SHA-256 in the generator; a mismatch is a hard error, so an upstream
revision has to arrive as a deliberate commit that re-pins the hash rather than as a silent
change in what this crate decodes. The full URL, revision and hash of every table are also
recorded in the header of the generated `src/tables.rs`.

The generator does not just transcribe. It rejects a table in which any byte below `0x80` maps
to anything but itself (which is what makes the 128-entry layout sound), any mapping outside the
BMP or onto a surrogate, and any table where two bytes share a Unicode target — the last is what
makes `encode_char` single-valued rather than arbitrary.

**Independent cross-check.** All twelve generated tables were diffed byte-for-byte against
CPython's own `encodings.cp125x` / `cp437` / `cp850` / `mac_roman` codec tables, which are a
separate derivation of the same mappings: **zero disagreements across all 12 × 128 entries**,
undefined slots included.

## Where the authoritative sources disagree

Two real conflicts, both documented in the API rather than resolved silently.

1. **The C1 holes.** The Unicode Consortium's files mark thirty-odd byte values across the nine
   Windows-125x pages as *undefined* — Windows-1252 `0x81`, `0x8D`, `0x8F`, `0x90`, `0x9D` being
   the famous ones. Windows' own `MultiByteToWideChar` and the WHATWG Encoding Standard (so
   every browser, and `encoding_rs`) instead map each to the C1 control of the same number:
   `0x81` → U+0081. Diffed against the WHATWG indexes, that accounts for **every** divergence in
   Windows-1250/1251/1252/1253/1254/1257/1258 and all but one in 1255.

   Which is right depends on where the bytes came from: text a Windows API produced round-trips
   only under the lenient reading, text from a strict transcoder never contains those bytes at
   all. So `decode_byte` follows the Unicode files and returns `None`, and
   `decode_byte_lenient` follows Windows. Neither is silent.

2. **Windows-1255 `0xCA`.** The one substantive disagreement outside the C1 range: the pinned
   `CP1255.TXT` (2000) leaves it undefined; the WHATWG index maps it to U+05BA HEBREW POINT
   HOLAM HASER FOR VAV, a character encoded in 2004. This crate follows the pinned file, and
   `decode_byte_lenient` deliberately does *not* paper over it — there is no "same value"
   fallback for a byte outside `0x80..=0x9F`, and inventing one would hide a genuine mapping
   dispute behind a mechanical rule.

   Mac OS Roman, by contrast, agrees exactly between Apple's `ROMAN.TXT` c02 and the WHATWG
   `macintosh` index on all 128 high bytes — including `0xDB` = EURO SIGN (it was CURRENCY SIGN
   before Mac OS 8.5) and `0xBD` = U+03A9 (the canonical decomposition, not U+2126 OHM SIGN).

## The parts that are easy to get wrong

- **Windows-1252 is not ISO-8859-1.** `0x80..=0x9F` are C1 controls in Latin-1 and printable
  punctuation in Windows-1252 — the euro sign, the curly quotes, the dashes. This is the single
  most common source of mojibake in clipboard text. The corpus carries the same 22 bytes twice,
  as `cp1252-smart-quotes.bin` and `latin1-same-bytes-as-cp1252.bin`, so a regression that
  confuses the two fails a test rather than shipping.
- **Undefined is not U+FFFD.** Seven of the nine Windows-125x pages leave some byte unassigned;
  Windows-1255 leaves twenty-three. `decode_byte` returns `None` and `Decoder` yields
  `ErrorKind::Malformed` at the offending offset. Substituting a replacement character is
  available from `decode_byte_lossy` / `decode_to_string_lossy`, by name.
- **`Malformed`, not `Unsupported`.** An undefined byte is well-formed input in an encoding this
  crate *does* implement; the code page simply assigns it no character. `Unsupported` is
  reserved for `encode_from_str` meeting a character the page cannot represent.
- **One bad byte does not end the string.** Unlike `Utf16Le`, which stops at a lone surrogate
  because everything after it is suspect, `Decoder` reports an undefined byte and carries on. A
  single-byte encoding cannot lose sync: byte *n* says nothing about byte *n+1*.
- **Combining marks are normal output.** Windows-1255 (Hebrew points), 1256 (Arabic marks) and
  1258 (Vietnamese tone marks) map ordinary bytes to combining characters. Every mapping here is
  still one byte to one `char`, so the iterators stay 1:1 — but the decoded text has more
  `char`s than grapheme clusters, and anything truncating by `char` count will cut a letter off
  its mark. `cp1258-vietnamese.bin` and `cp1255-hebrew-points.bin` pin that.
- **Decoded 1258 text is not NFC.** CP1258 spells `ế` as `ê` + U+0301, so a round-trip through
  a normalizing layer changes the bytes.

## Size

Twelve tables of `[u16; 128]` — **3,072 bytes of `rodata`**, and only for the encodings actually
referenced, since each is a separate `const`. ISO-8859-1 costs nothing at all: its high half is
the identity map, so it has no table. The high half is the whole table because every encoding
here is verified ASCII-transparent below `0x80`.

## Prior art

Six candidates were built and run — sources extracted, `cargo tree -e normal`, cross-compiled to
`thumbv7em-none-eabi`, and every byte `0x00..=0xFF` decoded through each. **Verdict: none is a
fit, tables generated in-house.** Not for want of trying; the reasons are specific.

- **[`encoding_rs`](https://crates.io/crates/encoding_rs)** (0.8.35) — excellent, and the wrong
  tool here. It has no CP437 and no CP850 **and never will**: its scope is the WHATWG Encoding
  Standard, which does not include them, so RTF's `\pc` and `\pca` are simply out of reach
  (`for_label("ibm437")` → `None`). It also cannot give true ISO-8859-1 through the `Encoding`
  API — `for_label("iso-8859-1")` returns *windows-1252*, per WHATWG's unification — so the one
  distinction this workspace most needs requires detouring into `mem::decode_latin1`. On top of
  that: 264 `unsafe` sites (raw-pointer SIMD), a 2.5 MB `data.rs`, and **+161 KB** stripped for
  nine Windows pages plus Mac Roman, against 3 KB here. `no_std` does work. Rejected on coverage
  first, size and `unsafe` second.
- **[`codepage`](https://crates.io/crates/codepage)** (0.1.2) — the codepage-number→encoding
  lookup, and `no_std`, but it is a thin map onto `encoding_rs` and inherits every problem
  above: `to_encoding(437)` and `to_encoding(850)` return `None`, and `to_encoding(28591)`
  returns **windows-1252**, which is exactly the wrong answer for a legacy RTF path (`0x80`
  would become U+20AC instead of U+0080). Rejected.
- **[`yore`](https://crates.io/crates/yore)** (2.1.1) — the closest of the six, and genuinely
  good: zero dependencies, three-tier `no_std` down to no-allocator, allocation-free
  `decode_byte` / `encode_char`, actively maintained, and it ships the nine Windows pages plus
  437 and 850. But it has no Mac Roman, no ISO-8859-1, no code-page-number lookup, 16 `unsafe`
  sites, and — decisively — its Windows-125x tables are `Complete`, with the C1 holes filled in
  with C1 controls, so `decode()` *cannot* report an undefined byte. Rejected: it would have
  needed four additions and the removal of `unsafe` to reach parity with 300 lines of generated
  table.
- **[`oem_cp`](https://crates.io/crates/oem_cp)** (2.1.2) — OEM pages only, no Windows-125x at
  all. Good design (`[char; 128]`, `Option<char>` for incomplete pages, +16 bytes for 437 and
  850) and effectively `unsafe`-free, but it covers two of the thirteen encodings needed and
  pulls in `phf` + `phf_shared` + `siphasher`. Rejected on coverage.
- **[`encoding`](https://crates.io/crates/encoding)** (0.2.33) — unmaintained since 2016, six
  transitive deps, **fails to compile without `std`**, and under `DecoderTrap::Strict` still
  returns `Ok` for Windows-1252 `0x81`. Rejected.
- **[`codepage-strings`](https://crates.io/crates/codepage-strings)** (1.0.2) — the only crate
  with a complete code-page-number map, but ten transitive deps (`ahash`, `getrandom`, `libc`,
  `zerocopy`, `lazy_static`, …), **fails to compile without `std`**, and forces a `Cow<str>` on
  every decode. Rejected.

`simple-encoding` does not exist on crates.io. `charset` is `encoding_rs` plus base64 for email
UTF-7 — same encoding set, one more dependency, no code page numbers.

The pattern across all six is worth stating plainly, because it is the reason this crate exists
rather than a wrapper: **every one of them silently fills the C1-range holes with C1 control
characters.** Not one can tell a caller that Windows-1252 `0x81` is unassigned. For a clipboard
codec, where the whole job is refusing to invent text that was not there, that is the one
property that could not be given up.

## Not implemented

- **Multi-byte / DBCS code pages.** Shift-JIS, GBK, EUC-KR, Big5. They are stateful and need a
  different shape of parser; `from_windows_codepage` returns `None` rather than pretending.
  Word emits these for `\fcharset` fonts, so this is the most likely next addition.
- **The rest of the ISO-8859 family**, and the Mac non-Roman scripts (`x-mac-cyrillic`,
  10001–10008). Adding one is a line in `generate/generate.py` plus a variant; nothing in scope
  references them yet.
- **Best-fit encoding.** `encode_char` maps a character or fails. It will not substitute `"` for
  `\u{201C}` the way Windows' `WC_NO_BEST_FIT_CHARS`-less default does, because a best-fit table
  turns a lossless round-trip into a silently lossy one.
- **Charset detection.** Out of scope on purpose; see the crate docs.
